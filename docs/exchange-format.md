# Формат обмена dsh-exchange/1

Переносимый формат папки обмена: одна и та же папка структуры поднимает обмен в любом
воркспейсе, потому что в декларации нет машинно-зависимых путей.

## 1. Где лежит ящик

Ящик объявляет папка обмена — отдельный элемент списка `folders`, а не узел графа.
Узлы в структуре — только агенты (`nodes`): у папки нет роли, модели и расписания.

```json
{
  "nodes": [
    { "id": "coordinator", "role": "координатор", "model": "work" }
  ],
  "folders": [
    {
      "id": "folder-1",
      "box": { "path": "coordination", "root": "shared" },
      "exchange": { "threads": ["critic-report"], "contract": "contract.md" },
      "participants": ["structure", "workflow"],
      "orchestrator": "coordinator"
    }
  ]
}
```

| Поле | Смысл |
| --- | --- |
| `id` | имя папки в структуре |
| `box.path` | путь к ящику обмена; только относительный — переносимо |
| `box.root` | `shared` (по умолчанию) — от общего корня участников; `workspace` — внутри своего воркспейса |
| `exchange.threads` | ветки внутри ящика; пусто — все ветки |
| `exchange.contract` | файл контракта в корне ящика (`contract.md`) |
| `participants` | участники, минимум один: **метки** (`structure`, `workflow`) или абсолютные пути |
| `orchestrator` | id объявленного узла-оркестратора: связь папки с агентом — поле, а не ребро |

`box`, `participants` и `orchestrator` обязательны. Прежняя форма, где папка была
узлом (`{ "id": "folder-1", "kind": "folder", … }`), больше не принимается: структура
возвращает ошибку `folder-as-node` с рецептом «перенесите папку в список folders».
Неизвестный `orchestrator` — ошибка `folder-orchestrator-unknown`, отсутствующий —
`folder-orchestrator`.

`box.path` — только относительный, без `..` и без абсолютных путей: общая папка не может
оказаться вне своего корня (уточнение workflow --61 п.2). Если участники на разных дисках,
общего каталога нет — это ошибка конфигурации с названием всех путей, а не тихий откат
на один воркспейс (п.1).

`root: "shared"` разрешается от самого глубокого каталога, содержащего все воркспейсы
участников. Для `…/deepseek-harness/dsh-project-graph` и `…/deepseek-harness/default-workspace`
это `…/deepseek-harness`, значит `coordination` → `…/deepseek-harness/coordination`.
Тот же узел в другой паре воркспейсов даст свою папку — без правки файла.

Метка участника разрешается через карту профиля `participants` (`метка → путь`), затем
через `docs/exchange.md` и README канала. Абсолютный путь в `participants` по-прежнему
принимается: старые структуры продолжают работать.

## 2. Раскладка папки

```
<box>/
  README.md                     кто есть кто (таблица «метка → воркспейс»)
  docs/exchange.md              императив обмена, пишет панель Structure
  threads/<ветка>/<письмо>.md   письма
```

## 3. Имя письма

```
<ISO-дата>T<ЧЧ-ММ><±ЧЧ-ММ>--<from>--<NN>.md
2026-11-01T21-05+03-00--workflow--57.md
```

`NN` — порядковый номер автора в пределах ветки: `max(NN)+1` на момент записи
(`nextLetterNumber()`). Повтор номера — ошибка, а не перезапись (уточнение --61 п.3).
Имя уникально и сортируется по времени как строка.

## 4. Шапка письма

Обязательные поля — первые восемь; остальные по надобности. Порядок фиксирован, чтобы
шапку можно было читать частично (только заголовки), не открывая текст.

```
Format: dsh-exchange/1
From: workflow
To: structure
Date: 2026-11-01T21:05+03:00
Thread: critic-report
Status: answer
Session: session-b8721a2a-456c-48a2-94cd-8030d895a8e8
Subject: одна строка
Reply-To: threads/critic-report/2026-11-01T20-59+03-00--structure--44.md
Ref: threads/critic-report/2026-11-01T20-59+03-00--structure--44.md
```

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `Format` | нет | версия формата; отсутствие = совместимость с v1 |
| `From`, `To` | да | метки сторон |
| `Date` | да | ISO 8601 со смещением |
| `Thread` | да | ветка (совпадает с папкой) |
| `Status` | да | см. таблицу статусов |
| `Session` | да для приёмки | id сессии автора в форме `session-<uuid>` (голый uuid нормализуется); **сторону определяют по нему, а не по `From`**; письмо без `Session` — legacy v1, сторона по `From` (--61 п.5) |
| `Subject` | нет | одна строка, без переносов |
| `Reply-To` | для ответа | файл, в ветку которого отвечают |
| `Ref` | для ответа | на что именно отвечают (для `ack` обязателен) |
| `Rev` | для приглашения | ревизия контракта, на которую ссылается письмо |
| `Box` | для приглашения | **абсолютный** путь ящика: его передают в `join` как есть |

Тело — после пустой строки, подпись последней строкой: `— <метка>`.

## 5. Статусы

| Статус | Кто пишет | Будит адресата |
| --- | --- | --- |
| `request` | сторона с задачей | да |
| `question` | сторона с вопросом | да |
| `report` | исполнитель | да |
| `proposal` | инициатор | да |
| `agreed`, `rejected` | решение по предложению | да |
| `answer` | ответ на `request`/`question` | да, но ответ на `answer` не пишется |
| `ack` | подтверждение получения | нет |
| `invitation` | инициатор — приглашённому | да, **всегда**: это единственное исключение из гейта квитанции |
| `declined` | приглашённый — инициатору | да |

## 6. Правила

1. Файл письма неизменяем: правка — только дописыванием `EDIT <время>: …`. `EDIT` не будит
   адресата и не дублирует доставку: память доставленного ведётся по файлу, а не по mtime (--61 п.4).
2. На `request`/`question` — ровно один `answer`; на `answer` — только чтение.
   `answer` доставляется как отдельное письмо (одна запись на письмо), но доставленный `answer`
   нового письма не порождает: цепь заканчивается правилом, а не подавлением доставки
   (уточнение к --61 п.6: `--57` и `--61` сами `answer`, и оба доставлены отдельными записями).
3. `ack` обязателен для приёмки: он несёт `Ref` на принятое письмо.
4. Сторона — по `Session`; письмо без `Session` от поднятого агента не считается
   ни требованием, ни подтверждением.
5. Доставка идёт в сессию адресата (`sessionController.prompt`), двойники не поднимаются.
6. Сессия, занятая маршрутом субагентов, адресатом не считается — берётся следующая.

## 7. Совместимость

Формат v1 = то, что уже лежит в `coordination/threads/critic-report`: существующие письма
читаются без правок (нет `Format` — считаем v1). Новые письма пишут `Format: dsh-exchange/1`,
чтобы будущая версия могла отличать их, не ломая старые. Неизвестные поля шапки игнорируются;
`Format` новее известного — письмо принимается, в лог пишется `format: unsupported` (--61).

## 8. Контракт, подключение и жизненный цикл папки

### Папка и выходы

- Папка обслуживает **воркспейсы**. Внутри воркспейса с папкой работает его **координатор**:
  именно он указан в поле `orchestrator` папки. Прочие агенты общаются через координатора,
  прямых выходов у них нет.
- Обменных папок может быть несколько, и они изолированы друг от друга: у каждой свой
  `box` и свой контракт. Участник канала X не читает канал Y, если не участвует в обоих.
- Прокси (воркспейс ретранслирует между двумя папками) — поведение его координатора, а не
  свойство портала.

### Контракт

Контракт — манифест в корне ящика (`contract.md`), написанный инициатором:

```
Format: dsh-exchange/1-contract
Portal: <нормализованный путь ящика>
Rev: 3
Initiator: structure
Invited: workflow, school
Created: 2026-11-02T00:24+03:00
```

- Контракт **мутабелен, но версионируется**: каждое добавление/исключение участника — новая
  ревизия (`Rev+1`), событие остаётся в истории, а не затирается.
- Квитанция ссылается на конкретную ревизию, поэтому «кого исключили и когда» проверяемо.

### Состояния папки

| Состояние | Условие | Поведение
| --- | --- | --- |
| **черновик** | 1 участник, обмена не было ни разу, контракта нет | письма с нулевым адресатом; никто не может подключиться |
| **портал** | ≥2 участников, контракт есть | доставка тем, кто прислал квитанцию |
| **архив** | участников убавили до 1, а обмен уже был | данные читаются, доставка погашена |

Различие «черновик / архив» — не по числу участников, а по тому, **был ли обмен хотя бы раз**
(был контракт или было доставлено письмо). Минимальное число участников — всегда 1: инициатора
исключить нельзя.

### Состояния участника

```
invited ──квитанция accepted──▶ accepted ──отключение──▶ disconnected
```

- `invited` — сторона в контракте, но связь не работает; доставки к ней нет.
- `accepted` — прислала квитанцию (`Status: accepted`, `Ref` на ревизию контракта, свой `Session`);
  с этого момента доставка включена. Подтверждение инициатора не требуется — он уже в контракте.
- `disconnected` — отключена (сама или инициатором). Отключение вежливое: в ящик кладётся
  `Status: disconnected` с `Ref` на квитанцию, чтобы вторая сторона не ждала ответа.

### Приглашение

`Rev+1` не только переписывает контракт, но и **приглашает**: каждый участник папки, который
ещё не ответил квитанцией (`accepted` или `disconnected`) и не является инициатором, получает
письмо в первую ветку папки (`exchange.threads[0]`, иначе `critic-report`):

```
Format: dsh-exchange/1
From: structure
To: workflow
Date: 2026-11-02T18:00+03:00
Thread: critic-report
Status: invitation
Session: session-b8721a2a-456c-48a2-94cd-8030d895a8e8
Ref: contract.md
Rev: 2
Box: C:\work\deepseek-harness\coordination
Subject: приглашение в папку обмена
```

- `Ref` — имя контракта относительно ящика, `Rev` — новая ревизия, `Box` — **абсолютный** путь
  ящика: приглашённый не может вывести его из метки, поэтому путь передаётся прямо в шапке.
- Имя письма — по общему правилу §3 (`nextLetterNumber()`), повтор номера не допускается.
- **Доставка приглашения — исключение из гейта квитанции** (см. «Состояния участника»): письмо
  `Status: invitation` доставляется адресату всегда, даже когда он ещё `invited`. Иначе
  получается дедлок: квитанцию нечем выдать, пока приглашение не дошло. Остальные письма
  по-прежнему ждут в ящике до квитанции.
- Повторный `contract` приглашает снова тех, кто так и не ответил: приглашение не «одноразовое».

### Подключение и отказ (join / decline)

Приглашённый отвечает одним из двух действий папки; оба пишут письмо в ящик, но `join` ещё и
заводит папку в своей структуре.

- `join` — тело `{ id, box, participants, orchestrator }`, где `box` — **абсолютный** путь из
  шапки приглашения. Папка записывается в `structure/graph.json` приглашённого: `box.path`
  вычисляется относительно его воркспейса (`root: workspace`, если ящик внутри), иначе —
  относительно общего каталога участников (`root: shared`); абсолютный путь в структуру не
  попадает. Затем пишется квитанция `Status: accepted` с `Ref` на контракт — та же, что у
  действия `accept`.
- `decline` — тело `{ id, box?, session? }` (`box` нужен, если папки в структуре ещё нет).
  Пишет письмо `Status: declined` с `Ref` на контракт; структура не меняется — отказ и есть
  отсутствие подключения.

### Подключение и отключение (интерфейс)

- Команда «подключиться»: плагин обходит ящики, читает контракт, ищет в нём своё имя — и
  предлагает принять приглашение. Подключение — только явным действием пользователя.
- Отключение доступно обеим сторонам: из интерфейса этого воркспейса или инициатора.
- Повторное включение — новая ревизия контракта **и** новая квитанция: старые приёмы истекли.

### Удаление папки

Убрать всех участников (до 0) — эквивалентно удалению папки. Операция разрушительная и
выполняется только с предупреждением: удаление папки **отключает от данных**, которые в ней
накоплены (сами файлы при этом остаются на диске, панель их больше не показывает).
