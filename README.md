# dsh-project-graph

Read-only **structure of a project** inside [DeepSeek Harness](https://github.com/deepseek-ai):
who is in the project, which model each role runs on, and how the members are
linked. The structure is a declaration in the repository (`structure/*.json`); the
panel only shows it. One action exists beside the panel: the
`project_graph_spawn` tool starts one agent for one node, on the model the
declaration assigns.

Это тонкая надстройка: своя только декларация, её проверка и один инструмент.
Агентов порождает системный плагин DSH (`ctx.subagents`); панель отвечает на
вопрос «как устроен проект», а инструмент — на вопрос «кого позвать на эту
работу и на какой модели».

## Что показывает

- узлы: идентификатор, роль, модель, краткое назначение (`brief`);
- связи четырёх видов: `delegate` (поручение), `review` (проверка),
  `report` (возврат результата без оценки), `peer`
  (сотрудничество равных, ненаправленное);
- ошибки и предупреждения валидатора рядом с графом;
- какие файлы сложились в структуру (`sources`).

Карточка узла — меню **«Что дальше»**: «Связь» (delegate/review/report/peer с выбором
направления и узла), «Изменить узел» (роль, назначение и модель из объявленных,
без сборки), «Запустить узел» и «Запустить ветку» — последние два не запускают
агента, а готовят вызов `project_graph_run` / `project_graph_branch` с
параметрами глубины и параллельности: панель не имеет сессии, вызов выполняет
модель в чате. Кнопка запуска у узла без модели видна, но объясняет, почему
недоступна.

Простые правки не требуют сборки: кнопка **«Добавить узел»** над схемой пишет узел
сразу в `structure/*.json` (id, роль, модель из объявленных, назначение), а сборка
остаётся для моделей и больших перестроек. Из сборки всегда есть выход —
**«← К схеме»** в верхней панели и в шапке самой сборки, а также клавиша Esc;
несохранённые правки сборки при возврате теряются, об этом сказано на экране.

Структура может быть **одноранговой**: корень не обязателен, корней может быть
несколько, и граф может состоять из одних `peer`-связей.

## Требования к панели

Четыре императива заказчика — ошибки с рецептом, пояснение на каждом элементе,
видимые варианты развития от узла и открытие в текущем воркспейсе с человеческой
инструкцией, если структуры нет: [docs/imperatives.md](docs/imperatives.md).
Образец подачи — панель Workflow.

Бэклог: [docs/BACKLOG.md](docs/BACKLOG.md). Блочная раскладка команд:
[docs/block-layout.md](docs/block-layout.md).

## Установка

Три пути, все ставят один и тот же пакет.

**1. Tarball из релиза (рекомендуется).** Не требует git и не тянет dev-зависимости:

```powershell
pnpm add https://github.com/AleksandrGoriachev/dsh-project-graph/releases/download/v1.0.27/dsh-project-graph-1.0.27.tgz
```

Проверено: ~2 секунды, ставится один пакет без зависимостей.

**2. Git-репозиторий.** Работает, если на машине есть `git` и нет блокирующих политик pnpm:

```powershell
pnpm add https://github.com/AleksandrGoriachev/dsh-project-graph
```

Если установка из UI DSH висит («pnpm printed nothing for 600000ms»), это транспорт, а не пакет:
у pnpm 10 гит-зависимость разрешается через `git` и локфайл-политику. Проверьте `git --version`,
запустите ту же команду в терминале с `--reporter=append-only` — или используйте путь 1.

**3. Из локальной копии:**

```powershell
git clone https://github.com/AleksandrGoriachev/dsh-project-graph
pnpm add .\dsh-project-graph
```

Плагин объявляет свой patch-слой:

```yaml
# cordis.patch.yml
- insert:
    - id: dsh-project-graph
      name: dsh-project-graph
      config:
        roots: []            # абсолютные пути проектов; первый выбирается по умолчанию
        structureDir: structure
        provider: spawn      # провайдер ctx.subagents для инструмента
```

Панель появляется вкладкой **Structure** рядом с представлениями диалога и
читает проект по GET-маршрутам `/project-graph/api/*` и создаёт стартовую структуру
одним `POST /project-graph/api/init` — только по кнопке и только если структуры ещё нет;
на выбор четыре стартовых графа: иерархический, одноранговый, смешанный и «без
оценщика».

## Запуск и результат

Два инструмента, одна маршрутизация:

- `project_graph_spawn` — запускает узел и сразу отдаёт `childId`, не дожидаясь результата;
- `project_graph_run` — запускает узел с `delivery: caller` и **ждёт** результат: возвращает
  `status: ok | error | timeout`, `output`, `durationMs` и пишет состояние в
  `/api/activity` (`running → done | error`).

Таймаут — `timeoutMs` (1с..30мин, по умолчанию 10мин). Состояния видны в
карточке узла: «работает», «завершил» с временем, «ошибка» с сообщением.

### Ветка по `delegate`

`project_graph_branch` запускает не один узел, а ветку: стартовый узел, затем его
соседи по рёбрам `delegate`, уровень за уровнем.

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `node` | — | с какого узла начинается ветка |
| `prompt` | — | задание первому узлу; дальше уровень получает результаты предыдущего |
| `depth` | 2 | сколько уровней строить, 1..5; 1 — только стартовый узел |
| `parallelism` | 2 | сколько узлов одного уровня идут одновременно, 1..16 |

Правила:

- **`review` не идёт автоматически**: приёмка всегда отдельный шаг, иначе проверка
  превращается в побочный эффект делегирования;
- **ошибка останавливает ветку**: новые узлы не запускаются, уже запущенные
  дорабатывают, ответ называет `failedNode` и причину — «где именно и что именно»;
- **каждый шаг — обычный запуск**: та же проверка маршрута, та же запись
  `running → done | error` в `/api/activity`, плюс общий `branchId`, чтобы шаги
  одной ветки было видно вместе;
- **готовый результат уровня уходит вниз**: следующий уровень получает текст
  «[узел] результат», поэтому ребёнок видит, что сделали до него;
- **шаги ветки видны в карточке**: у запусков общий `branchId`, панель
  показывает строку «Ветка — шагов N: узел — состояние…», а полный id — в
  подсказке. История запусков хранится на диске (до 200 записей на проект),
  поэтому ветка не исчезает после следующего запуска того же узла.

Пределы по умолчанию задаются в конфиге плагина: `branchDepth` и
`branchParallelism`; вызов может их сузить (`depth`, `parallelism`), но не
расширить за 5 и 16.

## Порождение агента

Инструмент `project_graph_spawn` доступен модели, когда в сборке есть
`tools` и `subagents`:

```json
{ "node": "critic", "prompt": "Проверь отчёт аналитика", "root": "C:/work/project", "plan": false }
```

| Параметр | Обязателен | Смысл |
| --- | --- | --- |
| `node` | да | id узла из `structure/*.json` |
| `prompt` | да | задание ребёнку |
| `root` | нет | абсолютный корень; обязателен, если корней несколько |
| `plan` | нет | только показать маршрут, никого не порождая |

**Модель выбирает декларация, а не вызов.** Пресет (`nodes[].agentPreset`) уходит в `request.agentPreset`, поэтому роль получает состав и инструменты пресета; без него ребёнок наследует пресет родителя. Узел ссылается на алиас в
`models`, алиас даёт `provider/model`; они уходят в `agentOptions`
субагента. Поэтому маршрут проходит git-ревью вместе со структурой, а
`allowedModels` инструмента `subagent` здесь ни при чём: модель не
выбирает модель.

Роль попадает в `label` (`role:node`), поэтому уведомление о завершении и
каталог детей несут роль. Глубину задаёт политика DSH
(`ctx.subagents.resolveMaxDepth`), свой счётчик плагин не заводит.

Отказы (код в тексте ошибки и в `error.code`):

| Код | Когда |
| --- | --- |
| `no-roots` / `root-required` / `root-not-allowed` | корень не задан, неоднозначен или вне списка |
| `structure-invalid` | структура прочитана, но валидатор нашёл ошибки |
| `unknown-node` | узла с таким id нет |
| `node-without-model` | у узла нет модели: роль осталась декларацией |
| `spawn-unavailable` | нет `ctx.subagents`, провайдера или он не умеет `agentOptions` |
| `no-parent` | инструмент вызван без агента-родителя |
| `unknown-preset` | у узла `agentPreset`, которого нет в DSH (в тексте — список доступных) |
| `preset-unavailable` | узел требует пресет, но служба `agentPresets` не подключена |
| `preset-broken` | пресет объявлен, но не активируется |

## Формат структуры

Одна папка на проект — `structure/`. Каждый `*.json` в ней считается фрагментом;
фрагменты складываются, поэтому структура может вырасти из одного файла без смены
схемы.

```json
{
  "version": 1,
  "models": {
    "work":   { "provider": "opencode", "model": "deepseek-v4.1-flash" },
    "critic": { "provider": "opencode", "model": "glm-5.3-flash", "family": "zhipu" }
  },
  "nodes": [
    { "id": "lead-code", "role": "lead", "model": "work", "brief": "координатор программистов" },
    { "id": "judge", "role": "acceptor", "model": "critic", "agentPreset": "standard", "mustDifferFrom": ["lead-code"] }
  ],
  "edges": [
    { "from": "lead-code", "to": "judge", "kind": "review" }
  ]
}
```

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `version` | нет | схема фрагмента; поддерживается `1` |
| `models.`*alias* | нет | маршрут модели: `provider`, `model`, необязательное `family` |
| `nodes[].id` | да | латиница, цифры, `._-`; уникален в структуре |
| `nodes[].role` | нет | роль словами проекта (не словарь плагина) |
| `nodes[].model` | нет | алиас из `models` |
| `nodes[].agentPreset` | нет | id пресета DSH: состав, инструменты и персона ребёнка; пусто — наследует пресет родителя |
| `nodes[].brief` | нет | одна строка о назначении узла |
| `nodes[].mustDifferFrom` | нет | узлы, с которыми **запрещено** совпадать по семейству модели |
| `edges[].from` / `.to` | да | существующие узлы; петля — ошибка |
| `edges[].kind` | нет | `delegate` (по умолчанию), `review`, `report`, `peer` |

### Правила валидатора

Ошибки (структура недействительна):

| Код | Когда |
| --- | --- |
| `no-fragments` | в `structure/` нет ни одного `*.json` |
| `no-structure-folder` | в проекте нет папки со структурой |
| `invalid-json`, `invalid-fragment` | файл не JSON или не объект |
| `unsupported-version` | `version` не равна 1 |
| `invalid-node-id`, `duplicate-node` | идентификатор недопустим или повторён |
| `unknown-model` | узел ссылается на алиас, которого нет в `models` |
| `model-conflict` | один алиас объявлен по-разному в разных фрагментах |
| `unknown-edge-endpoint`, `self-loop` | связь ведёт в никуда или в себя |
| `unknown-edge-kind` | вид связи вне `delegate/review/report/peer` |
| `delegate-cycle` | цикл по `delegate` (по `peer` циклы разрешены) |
| `same-family` | `mustDifferFrom` нарушен по семейству модели |
| `empty-graph` | фрагменты прочитаны, но узлов нет |

Предупреждения (структура читается, но неполна): `no-model`, `no-role`,
`isolated-node`, `no-delegate-edges`, `duplicate-edge`,
`uncomparable-difference`. Одноранговая структура (только `peer`) законна и
предупреждения `no-delegate-edges` не даёт; оно остаётся для графа, где нет ни
`delegate`, ни `peer`.

## Сборка произвольного графа

Кнопка **«Собрать»** открывает форму: модели (алиас → выбор провайдера и
модели из `/api/models`), узлы (id, роль, модель, **пресет из списка**, назначение) и связи
(`delegate`, `review`, `report`, `peer`). Под узлами объясняется, что пресет — это
состав агента (персона, инструменты, модель по умолчанию), а без пресета узел
наследует пресет родителя; под выбранным пресетом показывается его описание. Если список моделей недоступен, остаются поля
для ручного ввода.
Это не шаблон — граф любой формы, в том числе без оценщика и с несколькими
корнями.

Строки моделей и узлов редактируются: «✎» заполняет форму, «Сохранить
модель/узел» применяет. У модели меняются provider/model (алиас остаётся,
потому что на него ссылаются узлы); у узла меняются id, роль, модель, пресет
и назначение, а при смене id переписываются концы его связей.

**«Проверить»** прогоняет черновик через схему и проверяет, что структуру
действительно можно реализовать в этом DSH:

- маршруты моделей: `llm.listProviders()` / `llm.listModels()` — провайдер и
  точная модель должны существовать;
- пресеты узлов: `agentPresets.resolve()` — пресет должен быть и не быть
  сломанным;
- провайдер субагентов: зарегистрирован и умеет `agentOptions` (и
  `agentPreset`, если у узлов есть пресет);
- схема: дубли, неизвестные концы, петли, циклы `delegate`, `mustDifferFrom`.

**«Создать»** пишет один `structure/graph.json`. Если структура уже есть,
панель спрашивает подтверждение; если она разбита на фрагменты (`models.json`,
`teams/*.json`) — отказывает, чтобы молча не потерять блок. Это запись файла,
а не запуск агентов: порождение по-прежнему идёт через `project_graph_spawn`.

## Иерархия и workflow-плагин

Если выбрать «Создать иерархическую», панель проверяет `GET /workflow/api/status`.
Плагин установлен — структура создаётся сразу. Не установлен — появляется
карточка: что даёт workflow (доска задач, карточка, политика; агентов он не
запускает), ссылки на [репозиторий](https://github.com/AleksandrGoriachev/subagent-workflow)
и `plugin/`, «Проверить снова» и «Создать без плагина». Иерархию можно
создать и без плагина; проверка не блокирует.

### Внешняя связь (обмен с другими воркспейсами)

Под схемой — блок «Внешняя связь»: что реально пересекло границу воркспейса.
Факт = направление + время размещения + с кем; тексты сообщений не читаются.

- источники: папки из `exchange` в конфиге, затем соглашение — папка `coordination`
  рядом с воркспейсом;
- шапка сообщения: `From/To/Date` (плюс `Thread`, `Status`), без них файл не факт и
  показывается счётчиком «не разобрано»;
- текущий воркспейс — выбранный в панели; подписи связываются с воркспейсами картой
  `participants` (подпись → путь), иначе — по имени папки;
- тип связи по правилу заказчика: одно сообщение — односторонняя (исходящая, если
  источник — текущий; входящая, если адресат); два и более — разбор по адресатам,
  обмен в обе стороны — двусторонняя;
- «Сообщения (N)» раскрывает список фактов: время, направление, ветка, статус.

### Проверка соответствия схеме (fit): один корень, цепочка delegate и
покрытие исполнителей: результат либо проверяет оценщик (`review`), либо он
возвращается владельцу работы (`report` корню). Если нет ни того, ни другого,
панель показывает предупреждение «Workflow-схема: иерархия неполная» — это не
ошибка структуры, запуск и связи работают.

В этой рабочей структуре так и сделано: worker проверяется judge, а designer
возвращает результат координатору через `designer → coordinator (report)` —
поэтому предупреждения о нём нет. Возврат — не оценка и не поручение: слои он
не меняет, ветка по нему не идёт, и он рисуется пунктиром со своей стрелкой.

### Установка из карточки

Если в конфиге плагина задан `workflowInstallSpec`, карточка предлагает кнопку
**«Установить»**: панель не изобретает установщик, а передаёт строку штатному
`pluginManager.installBundle` (pnpm в профиле, откат `package.json` и
`pnpm-lock.yaml` при отказе). По схеме v1 (утверждена заказчиком 2026-10-28)
строка — стабильный ассет релиза:

```yaml
workflowInstallSpec: 'https://github.com/AleksandrGoriachev/subagent-workflow/releases/latest/download/dsh-workflow-console.tgz'
```

Исходы карточки:

| Исход установщика | Что видно |
| --- | --- |
| `applied` | «Установлено <версия>», статус перечитан |
| `restart-required` | «Плагин установлен, но нужен перезапуск DSH» и причина |
| отказ (`already-installed`, `not-bundle`, `incompatible-version`, `not-found`, `network`, `invalid-spec`) | причина + что сделать; хвост вывода pnpm при сбое загрузки |

Установленным считается только ответ `200` с непустым `plugin.name`; пустой
`404` — маршрут не зарегистрирован (например, до перезапуска после установки).
Повторная установка поверх отклоняется: обновление tarball — удалить плагин
(«Настройки → Плагины») и поставить заново. Спека не задана — кнопки нет,
остаётся ручная инструкция.

### Полоса Workflow и кнопка обновления

Над схемой стоит отдельная полоса **Workflow** со своим состоянием и своими
кнопками — чтобы установка и обновление не путались с действиями панели:

| Состояние | Что в полосе |
| --- | --- |
| плагин установлен, движок в проекте есть | **«Проверить актуальность»**, подпись «движок 2.6.2» |
| плагин установлен, движка в проекте нет | **«Развернуть»**, «Проверить актуальность» |
| сборка устарела (по проверке) | строка «сборка устарела: плагин 0.7.0 → 0.7.1, движок 2.6.2 → 2.6.3» и причина, почему обновление здесь недоступно |
| плагин не установлен | текст, откуда плагин ставится (спека), и «Проверить Workflow» |
| идёт работа | «Разворачиваю…», «Устанавливаю…» |
| исход | «установлено 0.8.0», «нужен перезапуск DSH», причина отказа |

Установки и обновления из полосы **нет намеренно**: установщик DSH качает релиз
через pnpm, а в этой среде загрузка с GitHub не проходит проверку сертификата
(прокси/антивирус) — кнопка падала бы каждый раз. Полоса не обещает того, чего
не сделает: она показывает состояние и говорит, откуда плагин ставится. Установить
его можно из карточки (действие «Создать иерархическую» без плагина) или средствами
самого workflow; в среде с нормальным сертификатом карточка ставит пакет из
`workflowInstallSpec` и отвечает ошибкой `network` с рецептом, если загрузка не прошла.

**Актуальность проверяется явно.** Кнопка «Проверить актуальность» скачивает
стабильный tarball релиза (только по нажатию, не при загрузке страницы), читает из
него `package/package.json` и `package/vendor/VERSION` и сравнивает с установленным
плагином (из профиля) и развёрнутым движком (из `docs/subagent-workflow/VERSION`).
Если обе версии совпадают — показывается только информация. Если что-то отстало —
появляется строка о расхождении и рекомендация обновить плагин через интерфейс
самого workflow: панель не заменяет локальную кнопку обновления, пока загрузка
пакета в этой среде не проходит.

«Развернуть» — второе действие, и оно про другое: плагин живёт в профиле, а движок
workflow — внутри проекта (`docs/subagent-workflow`, `docs/tasks`). Панель читает его
состояние из `docs/subagent-workflow/VERSION` и показывает «движок не развёрнут»,
пока его нет; кнопка вызывает маршрут панели workflow (`POST /workflow/api/deploy`,
0.7.0 и новее) с подтверждением и списком того, что появится. Если маршрута нет,
отказ говорит обновить панель workflow.

«Обновить Workflow» — это осознанная замена: панель спрашивает подтверждение и
предупреждает, что локальная установка папкой (`link:`) заменится пакетом из
`workflowInstallSpec`. На сервере это `POST /api/workflow-install?action=update`:
сначала `removeBundle` прежней версии, затем установка спеки; если удалять
нечего — установка всё равно выполняется, а сбой удаления показывается с
действием, а не выдаётся за успех.

В превью отсутствие плагина моделируется `PG_PREVIEW_WORKFLOW=missing`
(в этом режиме проверяются «Установить Workflow» и объяснённый отказ).

## HTTP

| Маршрут | Ответ |
| --- | --- |
| `GET /project-graph/api/status` | плагин, корни, папка структуры, виды связей |
| `GET /project-graph/api/projects` | список проектов со счётчиками узлов, связей, ошибок |
| `GET /project-graph/api/graph?root=<abs>` | граф, раскладка, ошибки, предупреждения, источники |
| активность | считается на клиенте по проекции `subagentCatalog` и `running` сессии; узла без метки `role:node` это не касается |
| `GET /project-graph/api/models` | провайдеры и доступные модели DSH для выбора в сборщике |
| `GET /project-graph/api/activity?root=<abs>` | последние запуски по узлам: `running`/`done`/`error`, время, сообщение |
| `GET /project-graph/api/presets` | пресеты DSH: id, имя, описание, сломанные |
| `POST /project-graph/api/check?root=<abs>` | проверить черновик графа: схема, модели в DSH, пресеты, провайдер субагентов; `200` с `ok` и ошибками |
| `POST /project-graph/api/build?root=<abs>&overwrite=true` | записать черновик в `structure/graph.json`; без фрагментов; `200`, конфликт — `409` |
| `POST /project-graph/api/link?root=<abs>&action=add\|remove&from=&to=&kind=` | добавить или удалить одну связь; внутри файла или в `links.json`; `200`, ошибка — `4xx` с рецептом |
| `POST /project-graph/api/init?root=<abs>` | создать `structure/graph.json` со стартовым графом; `template=hierarchy` (по умолчанию), `template=peer`, `template=mixed` или `template=team`; `201`, повтор — `409` |

Активный узел — тот, для которого прямо сейчас выполняется дочерняя сессия:
связь «сессия ↔ узел» по `label` вида `role:node`, которую ставит
`project_graph_spawn`. Рамка активного узла — 3px цветом роли и зелёная точка;
в деталях — состояние «работает». Если метки нет, узел не подсвечивается.

Только loopback. Чтение — `GET`/`HEAD`, запись — `POST /api/init` и
`POST /api/link`; корень вне списка `roots` — `400`. Существующую структуру
панель не перезаписывает: если в `structure/` уже есть `*.json`, создание
отклоняется с `409`.

## Проверки

```bash
pnpm install
pnpm test               # graph 21 + api 34 + client 15 + spawn 25 (95)
pnpm preview            # настоящий браузер: онбординг -> создание -> связь
```

`pnpm preview` поднимает локальный сервер с настоящим `createWebHandler` и
клиентским бандлом, подключает локальный React (без сети), создаёт временный
проект, проходит путь «пустой проект → иерархия → добавить peer → удалить» и
падает при ошибке в консоли. Скриншоты — в `preview-out/` (в git не входят),
временный проект удаляется. Первый запуск может потребовать
`pnpm exec playwright install chromium`.

Модель графа, валидатор и раскладка — чистые функции (`lib/graph.js`), проверяются
без DSH. HTTP-часть проверяется на мок-объектах запроса/ответа (`test/api.test.mjs`).
Клиент грузится поддельным `window.__ModuleLoader__` и обязан зарегистрировать ровно
один вид, не содержать PUT/DELETE и объяснять пустой проект человеку (`test/client.test.mjs`). Инструмент
порождения проверяется на мок-службе `subagents` и настоящей временной папке
структуры (`test/spawn.test.mjs`): каждый отказ обязан иметь стабильный код и не
доходить до `startActivation`.

## Границы

- Панель правит стартовую структуру, связи и собирает граф из форм. `POST
  /api/init` пишет стартовый файл, `POST /api/link` меняет одну связь, `POST
  /api/check` проверяет черновик, `POST /api/build` записывает его в один
  `graph.json` (фрагменты не перезаписывает). Сеть не используется.
- Инструмент ничего не пишет в проект: он читает декларацию и порождает одного
  агента. Граф целиком не запускается, кому делегировать — решает вызывающая
  модель.
- Чтение ограничено: 64 файла, 256 КБ на файл, только `*.json` внутри
  `structure/`.
- Только локальный провайдер `spawn`: роль должна переживать продолжение, а
  внешние (одноразовые) бэкенды этого не умеют.
- Роли здесь — слова проекта, а не словарь плагина: `analyst`, `lead`,
  `acceptor` — что угодно, лишь бы люди понимали друг друга.
