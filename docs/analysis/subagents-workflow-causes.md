# Субагенты: причины со стороны workflow

Источник тот же: 116 дочерних сессий, журналы DSH и run-store. Здесь — причины, которые создаёт контур задания/проверки, а не маршрут узлов.

## Сводка

| Показатель | Значение |
| --- | --- |
| Субагентов | 116 |
| Сессий с ошибками (строгий фильтр) | 95 |
| Ожидание/таймаут политики (`waitPolicy`) | **142 события в 68 сессиях (58,6 %)** |
| Нет файла job-лога/пути | 38 событий в 27 сессиях |
| Таймаут инструмента | 19 событий в 10 сессиях |
| Гейты task/review/accept | 6 событий в 5 сессиях |
| Повторные прогоны task+роль | 13 групп, 29 сессий, 16 лишних |

## Главные причины

### 1. `enforcement.waitPolicy=fail` — синхронные длинные команды запрещены
**Факт:** 142 события в 68 сессиях: `долгое ожидание (pwsh: timeoutMs=… ) запрещено политикой ... ожидайте тяжёлый прогон сторожем scripts/job.mjs`.

**Следствие:** почти каждый reviewer/judge сначала пробует `pwsh` на 240–600 с, получает отказ, затем переходит на `job.mjs`. Это добавляет шаги, задержки и иногда чтение несуществующего `.tmp/jobs/<id>.log`. Главный источник «долгих» прогонов не по делу.

### 2. Job-лог и пути: `not found` после запуска сторожа
**Факт:** 38 событий в 27 сессиях: `cannot read ... .tmp/jobs/<id>.log: not found`, `MISSING/ERR ... contract.md`, `ENOENT`.

**Следствие:** агент не видит результат уже запущенного job, повторяет ожидание/чтение; время растёт, полезной работы нет.

### 3. Повторные review/accept как штатный цикл
**Факт:** 13 групп task+роль; reviewer 0304, 0326, 0335 — по 3 прогона; 0331/0338/0308/0325/0321/0337 — по 2; judge 0331/0304/0326 — по 2. Всего 16 лишних прогонов.

**Причина:** rework/переписывание review, повторная проверка после правок, разные попытки контракта. Это не падение узла; это стоимость цикла. Триггеры в gate/contract, а не в коде продукта.

### 4. Таймауты инструментов
**Факт:** 19 событий в 10 сессиях: `tool call timed out after 30000ms` (grep/glob), `execution timed out ... 120000ms` (run_code).

**Следствие:** агент повторяет поиск/чтение; на больших `lib/*.js` это заметно. Часть — DSH-инструмент, не сам workflow, но политика запуска и размер проверок усиливают эффект.

### 5. Полный прогон тестов на каждом шаге
**Факт:** `panel-render` ~60 с в каждом verify; reviewer/judge нередко повторяют полный набор вместо точечного. Самый долгий reviewer 0317 — 58 мин, 0338 — 44 мин.

**Следствие:** время цикла складывается из повторных полных прогонов; сокращение — отбор тестов по изменённым файлам (уже в очереди движка).

### 6. Пользовательский abort
**Факт:** reviewer 0338, `turn/end reason=aborted/user` (44 мин, job killed). Это не дефект workflow; прерванный прогон не должен считаться падением.

## Отдельно: падения и таймауты узлов
- **Единственный таймаут узла:** worker `6219c40a` — `истекло ожидание 90000 мс`; причина в структуре (спавн/таймаут), не в workflow.
- **Единственное падение:** designer 0332 — 429 внешнего провайдера; причина в маршруте модели (структура), не в task-гейте.
- **Остальные 114** завершились `completed`; 16 повторных прогонов — rework, не падения.

## Что чинить в workflow
1. По умолчанию запускать длинные команды через `job.mjs`, не через синхронный `pwsh`: убрать 142 отказа и повторные чтения.
2. Гарантировать job-лог до возврата `job.mjs start` (или отдавать stdout в ответе); убрать `not found` (27 сессий).
3. Идемпотентность review: один review на контракт; повтор — только при изменённом контракте/явном rework; бюджет повторов.
4. Разделить «rework» и «повторный запуск»: счётчик попыток и причина в run-store.
5. Точечные тесты по изменённым файлам вместо полного panel-render на каждом шаге.
6. Таймауты инструментов: для grep/glob/read на больших файлах — больший бюджет или потоковый поиск.

## Ограничения
- 95 сессий с «ошибками» — эвристика по тексту; часть событий — чтение чужих логов, не отказ. Для точных цифр нужен структурный парсер `tool/result isError`, а не regex.
- 142 `waitPolicy` — реальные отказы инструмента, но не все приводят к потере времени: часть немедленно повторяется через job.mjs.
- Длительности — run-store; для 116 сессий нет отдельного статуса «ждёт job», поэтому max gap не разделён на модель/инструмент.
