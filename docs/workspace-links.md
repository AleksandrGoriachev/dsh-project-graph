# Связь между воркспейсами: устройство и настройка

Дата: 2026-10-28. Статус: **предложение к обсуждению**; шаг 1 уже сделан (см. §7).
Владелец документа: сторона `structure` (плагин панели).

## 0. Решения заказчика 2026-10-28

1. Связь показывает **реальных бенефициаров** процесса, а не обмен «координатор с
   координатором»: если работу получает дизайнер — на схеме видно дизайнера.
2. Если в записи и обмене участвует **наследник процесса** (участник уровнем ниже),
   схема обязана это отражать.
3. Идеал — плагин отражает **текущее состояние воркспейса, в котором работает**: в
   этом воркспейсе он сам должен обнаружить связь с workflow и показать её.
4. Показываются **только факты обмена**; то, что вне пространства, не показывается.

Экранный замысел заказчика: «на схеме отображается выход вне, и в нём обозначается
(по времени размещения сообщения) признак исходящего или входящего сообщения».
Дизайн этого поручен узлу `designer` — задание
`docs/tasks/0002/task.md` и спека `docs/design/workspace-exchange/brief.md`.

## 1. Что уже есть

| Возможность | Где | Состояние |
| --- | --- | --- |
| Панель читает любой воркспейс | `lib/api.js`: `roots` из конфига, иначе реестр DSH; `selectRoot(?root=)` | работает |
| Переключение проектов в панели | чипы над схемой | работает |
| Консоль workflow читает свой корень | `plugin/lib/api.js:38-48` — тот же принцип, `?root=` в маршрутах | работает |
| Запуск узла с указанием корня | `project_graph_run { node, root }`, проверка по `roots` | работает |
| Хранилище запусков | файл на корень, `~/.dsh/project-graph/runs/<hash>.json` | работает |
| Связь «агент ↔ агент» | папка `coordination/` (файлы-сообщения) | работает |

То есть **видимость** нескольких воркспейсов уже есть у обоих плагинов: у каждого
есть список `roots` и параметр `?root=` в маршрутах.

## 2. Чего не хватает

1. **Исполнение в чужом воркспейсе.** До этого изменения ребёнок запускался в
   каталоге вызывающей сессии. Структура проекта B, запущенная из сессии проекта A,
   читала и писала файлы A, хотя на карточке был узел B. Теперь `cwd` ребёнка =
   корень объявления узла (`lib/spawn.js`, тест «ребёнок работает в каталоге своего
   воркспейса»). Осталось проверить на живом процессе после рестарта.
2. **Явной связи нет.** Позвонить `root: B` можно, но в конфиге нигде не сказано,
   что эти два воркспейса связаны, кто в какой работает и к какой задаче относится
   работа. Панель показывает воркспейсы по отдельности.
3. **Связь с задачей.** Задача workflow живёт в воркспейсе B (`docs/tasks/0001`), а
   структура, которая её исполняет, — в A. Нигде не выражено, что это одна работа.

## 3. Предлагаемая настройка

Связь — это запись в конфиге моего плагина. Не ребро графа: см. §4.

```yaml
- id: dsh-project-graph
  config:
    roots:                       # пусто = все воркспейсы из реестра DSH
      - C:/Users/Goryachev/Documents/deepseek-harness/dsh-project-graph
      - C:/Users/Goryachev/Documents/deepseek-harness/default-workspace
    links:
      - id: design-for-wf                 # имя связи для вызова и для панели
        from: C:/Users/Goryachev/Documents/deepseek-harness/dsh-project-graph
        node: designer                     # необязательно: связь на уровне узла
        to: C:/Users/Goryachev/Documents/deepseek-harness/default-workspace
        kind: delegate                     # delegate | review | report
        task: docs/tasks/0001              # необязательно: задача в воркспейсе to
        note: "макеты интерфейса для задачи workflow"
```

Смысл полей:

- `from` — воркспейс, где объявлена структура и узел;
- `node` — узел этой структуры; без него связь описывает пару воркспейсов целиком;
- `to` — воркспейс, где работа действительно выполняется (становится `cwd` ребёнка);
- `kind` — тот же словарь, что у графа: `delegate` (работа), `review` (проверка
  чужими руками), `report` (возврат результата);
- `task` — путь к задаче workflow внутри `to`, чтобы консоль и гейты понимали,
  к какой работе относится запуск.

Вызов: `project_graph_run { node: "designer", root: from, link: "design-for-wf" }`.
Узел и корень берутся из `from`, `cwd` — из `to`, задача — из `task`. Неизвестная
связь — отказ со списком доступных (И-1), а не тихий запуск не туда.

Почему id, а не только пути: путь длинный и повторяется в каждом вызове; id
позволяет панели показать связь словами и проверить, что запуск соответствует
объявлению. Пути при этом остаются в конфиге, никакой магии с алиасами.

## 4. Почему не ребро графа

1. Слои, корень и полнота иерархии считаются **внутри одного графа**; ребро в
   другой воркспейс сломало бы раскладку и проверку (узел `to` не существует в
   этом `structure/graph.json`).
2. Валидатор проверяет, что концы связи есть среди узлов файла, — пришлось бы
   вводить «внешние» узлы, то есть дублировать чужие структуры.
3. Связь — это не то же самое, что зависимость в графе: один узел может работать в
   нескольких воркспейсах по очереди, и это не меняет структуру.

Поэтому связь живёт в конфиге, а панель показывает её отдельным блоком, не
смешивая со схемой.

## 5. Как это выглядит в панели

Блок «Связанные воркспейсы» рядом с полосой Workflow:

- `design-for-wf: designer (dsh-project-graph) → default-workspace, задача
  docs/tasks/0001` — с кнопкой «Скопировать вызов» (как у узла) и подсказкой, что
  панель сама агентов не запускает;
- статус по связи: последний запуск узла в этом воркспейсе и стадия задачи, если
  консоль её видит;
- если связь указывает на воркспейс вне `roots` — предупреждение с рецептом
  «добавьте путь в roots».

## 6. Что нужно от стороны workflow (к их релизу)

Ничего структурного: `roots` и `?root=` у них уже есть. Полезно договориться о
двух вещах:

1. **Идентификатор воркспейса в записи задачи.** Сейчас запись знает путь
   репозитория. Если их релиз покажет несколько корней, нужен стабильный id
   (путь — достаточный, если не переименовывать каталоги).
2. **Связка «задача ↔ запуск».** Хорошо бы, чтобы задача могла сослаться на
   `branchId`/сессию исполнителя; тогда панель и доска сойдутся без ручной сверки.

Это можно отправить им после релиза, чтобы не менять API в спешке.

## 7. Порядок внедрения

1. **Сделано:** `cwd` ребёнка = корень объявления узла (`lib/spawn.js`, тесты
   SPAWN, проверка на живом процессе — после рестарта).
2. `links` в конфиге: разбор, проверки (абсолютные пути, `to` внутри `roots`),
   `/api/status` отдаёт связи; тесты API.
3. Блок «Связанные воркспейсы» в панели с копируемым вызовом; тесты клиента и
   предпросмотра.
4. `link` в аргументах `project_graph_run`/`branch`: проверка, что `cwd` из связи,
   отказ при неизвестной связи; тест «запуск в другом воркспейсе».
5. Сквозной прогон: задача в B, структура в A, результат возвращается (`report`),
   панель и доска показывают одно и то же.

## 8. Безопасность

- только абсолютные пути; `to` должен входить в `roots` (или в объявленные связи)
  — иначе отказ;
- ребёнок получает `cwd = to`, но границы правок задаёт workflow через
  `allowedPaths` задачи, а не связь;
- панель по-прежнему только читает и отдаёт ссылки: кнопка «Скопировать вызов» —
  не запуск;
- ключи приёмки живут в воркспейсе задачи, связь их не переносит.

## 9. Ответы заказчика (2026-10-28) и что осталось

Ответы: связь — про реальных бенефициаров (п.1 решений), наследник процесса виден
(п.2), плагин обнаруживает связь сам в своём воркспейсе (п.3), показываются только
факты (п.4). Поэтому:

- `node` в связи — обязательное поле для узловых связей: показываем участника, а не
  «координатора вообще»;
- `from`/`to` остаются воркспейсами, но отображение крепится к узлу;
- обнаружение фактов обмена — часть дизайна (задание 0002), реализация — после
  выбора варианта.

## 10. Ответы заказчика (2026-10-28, вторая итерация)

1. **Писать в связанном воркспейсе можно.** Связь задаёт только `cwd`; границы
   правок — `allowedPaths` задачи workflow. Это разные вещи, и связь их не
   подменяет.
2. **`task` в связи не нужен.** Связь обслуживает воркспейсы, а не задачи: за время
   одной связи проходит несколько задач, и «задача в связи» устаревает в тот же день
   (начали с одной, закончили другой). Вместо этого по клику на выход открывается
   **список сообщений обмена** — для аналитики. Задачи остаются там, где им место: в
   консоли workflow.
3. **Граница «факта обмена»** (§12): факт = направление + время размещения + кто с
   кем. Источники в порядке приоритета: настроенные пути `exchange`, затем папка
   `coordination` рядом с воркспейсом (по соглашению), затем собственные записи
   плагина о запусках через связь. Тексты и чужое содержимое не читаются и не
   показываются; неразобранные файлы считаются и показываются числом.

## 11. Почему в связи нет `task`

Заказчик: «связь обслуживает не таски, а целые воркспейсы. Прошло несколько тасков —
эта информация ничего не даст. Начато с одним таском, закончено в другом».

Поэтому связь — это пара воркспейсов (и участник), без задачи. Аналитика задач
живёт в двух местах, и оба не в связи:

1. **Список сообщений обмена** по клику на выход — факты: время, направление,
   участник, ветка, статус (дизайн — задание 0002);
2. **Консоль workflow** — стадии задач и записи приёмки.

Если позже понадобится связать запуск с задачей, это будет поле **записи запуска**
(`taskId` в activity), а не конфига связи: запуск короткий, задача — тоже, а связь
долгая.

## 11а. Стандарт обмена в DSH: его нет

Проверено по установленной сборке 0.2.1-rc.3 (веб-поиск в этой сессии недоступен —
402 на поисковом эндпоинте, поэтому вывод по коду и документации пакетов):

- в 307 пакетах сборки нет ни одного с обменом между воркспейсами: есть
  `dsh-workspace` (воркспейс как контейнер сессий: путь, заголовок, привязка
  сессий), `dsh-api-workspace-*` (CRUD и файлы), `dsh-session-*` (история и
  поиск), `dsh-tool-session-query` (чтение истории);
- единственное «cross-workspace» в сборке — авторизация чтения истории сессий:
  запрос разрешён, только если `cwd` цели и вызывающего совпадают по строке. Это
  контроль доступа к чтению, а не протокол обмена;
- сообщения между агентами есть, но это `send_message` внутри одного хоста
  (сессия → сессия, родитель → ребёнок), а не стандарт обмена между воркспейсами.

Следствие по правилу заказчика: **связь маркируется как односторонняя**, пока нет
спеки обмена, по которой её можно проверить. Дизайн этой маркировки и самой спеки —
задание `docs/tasks/0003`.

## 11б. Правило классификации связи (заказчик, 2026-10-28)

Обменник — папка сообщений, один файл = одно сообщение; из шапки берутся `From`,
`To`, `Date`.

1. Одно сообщение в обменнике → связь односторонняя.
2. Источник — текущий воркспейс → исходящая односторонняя.
3. Адресат — текущий воркспейс → входящая односторонняя.
4. Два и более сообщений → разбор по адресатам: несколько односторонних связей или
   одна и более двусторонних.

**Текущий воркспейс — выбранный в панели в этот момент** (чип проекта / `?root=`),
а не константа. При переключении чипа выход и типы связей пересчитываются.

Метки шапки — подписи, не пути: `structure` в этом обменнике — это
`C:/Users/Goryachev/Documents/deepseek-harness/dsh-project-graph`. Связывание —
карта `participants` (подпись → абсолютный путь). Заказчик выбрал источник карты:
**конфиг плагина переопределяет, обменник даёт значения по умолчанию** (файл спеки
рядом с сообщениями); не привязана ни там, ни там — «не разобрано».

Алгоритм: разобрать шапки (без `From/To/Date` — «не разобрано»), перевести подписи в
воркспейсы по карте, отбросить чужие сообщения (текущего воркспейса нет ни в `From`,
ни в `To`), сгруппировать по паре «текущий — другой», и для каждой пары: только
исходящие → исходящая односторонняя; только входящие → входящая односторонняя; оба
направления → двусторонняя. Двусторонность — наличие фактов в обе стороны, а не
догадка; «ответа нет» — отсутствие входящих, а не таймер. Один и тот же обменник даёт
зеркальные типы для двух выбранных воркспейсов (для `structure`: 3 исходящих,
8 входящих; для `workflow`: наоборот), и обе стороны видят двусторонность.

## 12. Почему источники фактов именно такие

- **Настроенные пути** — предсказуемость: человек сам сказал, что считать обменом.
- **Соглашение `coordination`** — работает «из коробки» в этом воркспейсе: папка
  уже есть, сообщения уже пишутся с шапкой `From/To/Date`. Без неё в моём
  воркспейсе «выход вне» был бы пустым до ручной настройки — а заказчик просил,
  чтобы плагин сам отследил текущую связь.
- **Собственные записи** — единственный источник, который знает **узла** и точное
  время; остальные дают роль и время сообщения.

Почему не «читать чужой воркспейс»: это нарушило бы п.4 (что вне пространства — не
показывается) и дало бы панели права, которых у неё быть не должно. Факт — да,
содержимое — нет.

Время: `Date:` из шапки; время файла — только как запасной вариант с пометкой.
Участник: роль из шапки → узел по необязательной привязке `participants`, иначе
честная подпись «сессия <роль>». Путь чужого воркспейса из шапки не выводится.
