# Перевод проекта на хранение структуры в store

Текущий выпуск пакета — 1.0.91; что в нём изменилось — [RELEASES.md](RELEASES.md).

Инструкция для проекта, который держит структуру в репозитории (`structure/*.json`),
и для человека, который переносит её в store. Команды приведены дословно, рядом —
вывод, который печатает инструмент; повторить можно в любом проекте, подставив свой
абсолютный путь вместо `.`.

## Зачем переносить

Структура — данные воркспейса, а не исходник пакета: кто есть в проекте, какая у
роли модель, какие между ними связи. Пока она лежит в репозитории проекта, каждая
правка владельца делает рабочее дерево грязным, попадает в диффы и в обязательства
git-гейта. Store — папка вне репозитория, откуда её читают панель и
`lib/store.js`; формат фрагментов тот же, поэтому панель, сборка и
`project_graph_spawn` после переноса работают без изменений. Правило записано в
`docs/structure-rules.md`.

| Что | Где |
| --- | --- |
| каталог store | `$DSH_PROJECT_GRAPH_STORE`, иначе `~/.dsh/project-graph/<имя каталога проекта>-<sha1 корня, 8 hex>/` |
| граф | `<store>/graph.json` |
| связи | `<store>/links.json` |
| резервные копии | `<store>/backups/graph.backup-<ISO>.json.bak` |

Slug каталога — имя каталога проекта плюс короткий хеш абсолютного пути: два разных
каталога с именем `app` не должны делить один граф, а один и тот же каталог обязан
находить свой граф после перезапуска. Точный путь всегда печатает `--check` в строке
`store:`; на другой машине без `DSH_PROJECT_GRAPH_STORE` он будет другим, потому что
хеш считается от абсолютного пути.

## Как проект выбирает режим

Режим определяет наличие файлов, а не настройка:

- `режим: repo` — в `<проект>/structure/` есть хотя бы один `*.json`; структура
  читается на месте, store не используется. Это легаси-режим, не ошибка;
- `режим: store` — файлов структуры в репозитории нет (пустая папка ничего не
  объявляет); структура читается из store.

Отсюда порядок переноса: **сначала данные переезжают в store, потом репозиторий
очищается**. Если удалить файлы раньше, проект потеряет структуру до появления
store-копии; если не удалить вовсе, проект продолжит читать репозиторий и будет
говорить `режим: repo`.

## Шаг 1. Увидеть режим

Проверка ничего не пишет и ничего не меняет, код выхода — 0:

```powershell
node tools/migrate-structure.mjs --repo . --check
```

Ожидаемый вывод до переноса:

```text
Проверка структуры
  проект: C:\work\my-project
  папка структуры: structure
  режим: repo
  store: %USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d (my-project-1a2b3c4d)
  store-граф: нет (%USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d\graph.json)
  файл графа по резолверу: C:\work\my-project\structure\graph.json
```

Поля, на которые смотреть:

- `режим:` — то, что нужно изменить на `store`;
- `store:` — реальный путь store (`~/.dsh/project-graph/...` или значение
  `DSH_PROJECT_GRAPH_STORE`), его же показывает панель;
- `store-граф:` — есть ли уже граф в store (при первом переносе — «нет»);
- `файл графа по резолверу:` — что именно читает панель сейчас.

В Windows путь store в выводе показан как `%USERPROFILE%\.dsh\project-graph\...`,
на Linux и macOS — как `~/.dsh/project-graph/...`; слова и коды те же.

## Шаг 2. Посмотреть план без записи

```powershell
node tools/migrate-structure.mjs --repo .
```

Без `--apply` инструмент печатает план и заканчивает словами
`План: без --apply ни store, ни репозиторий не изменены.` (код выхода 0). План
называет источник, store, цель и счётчики: `узлов N, рёбер N, папок N, якорей N`.
Счётчики стоит запомнить — после переноса сверка обязана показать те же числа.

## Шаг 3. Перенести: `--apply`

```powershell
node tools/migrate-structure.mjs --repo . --apply
```

Порядок внутри инструмента безопасен и важен:

1. разбирается источник (`structure/graph.json`, при наличии `structure/links.json`),
   проверяется узел координатора и `buildGraph`;
2. preflight git: проект — репозиторий, а источник отслеживается (иначе `--apply`
   отказал бы уже после записи в store и оставил половинчатое состояние);
3. пишется резервная копия в `<store>/backups/` — имя оканчивается на
   `.json.bak`, а не на `.json`, иначе читатель принял бы копию за фрагмент
   структуры;
4. граф (и связи) записываются в store;
5. store перечитывается так, как его прочитает панель: режим `store`, канонический
   `structure/graph.json`, 0 ошибок `buildGraph`, **те же** узлы/рёбра/папки/якоря;
6. только после этой сверки файлы удаляются из репозитория через `git rm`.

Ожидаемый вывод (числа — свои):

```text
Перенос структуры в store
  проект: C:\work\my-project
  источник: C:\work\my-project\structure\graph.json
  store: %USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d (my-project-1a2b3c4d)
  цель: %USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d\graph.json
  граф: узлов 8, рёбер 7, папок 2, якорей 3 (в 3 узлах)
  резервная копия: %USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d\backups\graph.backup-2026-11-25T10-00-00-000Z.json.bak
  записано: %USERPROFILE%\.dsh\project-graph\my-project-1a2b3c4d\graph.json
  сверка store: readStructure — режим store, фрагментов 1 (structure/graph.json); buildGraph — 0 ошибок
  сверка: нормализованный JSON совпал (узлы/рёбра/папки/якоря)
  удалено из репозитория: structure/graph.json
  осталось в репозитории: в C:\work\my-project\structure файлов структуры нет
Перенос выполнен: структура этого проекта читается из store.
```

Если сверка не сошлась, инструмент отвечает `ОТКАЗ: …` и кодом выхода 1, а файл в
репозитории остаётся: store при этом уже записан, и вторая попытка увидит прежнюю
копию в `backups/`. Коды выхода:

| Код | Что значит |
| --- | --- |
| 0 | успех; повторный `--apply` после переноса отвечает `Проект уже в store` и тоже 0 |
| 1 | отказ или расхождение: источник не разобран, нет узла координатора, `buildGraph` нашёл ошибки, git не репозиторий, файлы не отслеживаются, сверка store не сошлась |
| 2 | ошибка аргументов или нечитаемый файл |

## Шаг 4. Проверить, что проект читается из store

```powershell
node tools/migrate-structure.mjs --repo . --check
```

Ожидаемый вывод: `режим: store`, `store-граф: есть (<путь>)`, а
`файл графа по резолверу` указывает внутрь store. Код выхода 0.

```powershell
git ls-files structure
```

Пустой вывод — правильный: ни один файл структуры не отслеживается. Если строка
появилась, удаление не сделано (или проект ещё в режиме `repo`).

## Шаг 5. Убедиться, что удаление не вернётся

`git ls-files structure` пуст сразу после `--apply`: удаление уже в индексе
(`git status --short` покажет `D  structure/graph.json`). Зафиксируйте удаление
коммитом штатным путём проекта — и проверьте, что история его не возвращает:

```powershell
git reset --hard
git ls-files structure
```

После коммита `git reset --hard` возвращает дерево к `HEAD`, а в `HEAD` файла уже
нет, поэтому `git ls-files structure` снова пуст. Пока удаление не в коммите, кнопка
отмены (`git reset --hard`) вернёт файл — это и есть причина фиксировать перенос
сразу. Вернуть структуру в репозиторий осознанно можно так:

```powershell
git show HEAD^:structure/graph.json > structure/graph.json
```

## Шаг 6. Правило `.gitignore` обязательно

В `.gitignore` проекта должна быть строка:

```text
/structure/
```

Почему это обязательное правило, а не украшение: папка-пустышка или случайно
созданный фрагмент в `structure/` мгновенно переводят проект обратно в
`режим: repo`, и панель начнёт читать пустой/устаревший файл вместо store. С
правилом такой файл не попадёт в git, а `git status` не станет грязным.

Проверка правила (выход 0, строка называет файл и строку `.gitignore`):

```powershell
git check-ignore -v structure/graph.json
```

Ожидаемый вывод:

```text
.gitignore:20:/structure/	structure/graph.json
```

Правило не заменяет удаление: файлы, уже отслеживаемые git, игнорирование не
убирает — их убирает `git rm` (это и делает `--apply`).

## Если в проекте остались свои файлы структуры

Так бывает, когда структура разбита на фрагменты (`structure/nodes.json`,
`structure/models.json`, `structure/teams/*.json`) и `structure/graph.json` в
репозитории нет: инструмент переносит только `graph.json` (и `links.json`), о
чём честно скажет. Порядок — **сначала перенос, потом удаление**; обратный порядок
теряет данные.

1. Убедитесь, что режим — `repo` и граф есть в репозитории:
   `node tools/migrate-structure.mjs --repo . --check`. Если инструмент отвечает
   `ОТКАЗ: нет файла структуры для переноса: …\structure\graph.json` (код 1),
   `--apply` пока невозможен.

2. Сведите фрагменты в один `structure/graph.json`. Фрагменты складываются в один
   граф, поэтому это перенос содержимого, а не догадка: `nodes`, `edges`,
   `models`, `folders` и `anchors` собираются в один объект, `version: 1`
   остаётся. Фрагменты-источники **пока не удаляйте**: перенос идёт по
   `graph.json`, и до сверки источник нужен на месте.

3. Перенесите граф: `node tools/migrate-structure.mjs --repo . --apply`. Инструмент
   запишет store и удалит `structure/graph.json`, но в конце честно скажет:
   `осталось в репозитории: …\structure — nodes.json, models.json`. Это значит,
   что режим пока `repo` и store не читается.

4. Удалите остатки — сначала из индекса, затем с диска:

   ```powershell
   git rm -r -f -- structure
   ```

   Неотслеживаемые файлы `git rm` не трогает; их удаляют вручную
   (`Remove-Item -Recurse -Force structure` в PowerShell, `rm -rf structure` в
   POSIX-оболочке). Правило `/structure/` из шага 6 держит папку пустой и дальше.

5. Снова проверьте режим — теперь он обязан быть `store`:

   ```powershell
   node tools/migrate-structure.mjs --repo . --check
   git ls-files structure
   ```

   `режим: store`, `store-граф: есть`, `git ls-files structure` — пусто. Если режим
   остался `repo`, значит в `structure/` ещё есть `*.json`: повторите шаг 4 и
   посмотрите `Get-ChildItem structure` / `ls structure`.

## Чек-лист готовности

- [ ] `--check` печатает `режим: store` и `store-граф: есть`;
- [ ] `git ls-files structure` — пусто;
- [ ] после коммита удаления `git reset --hard` файл структуры не возвращает;
- [ ] в `.gitignore` проекта есть `/structure/`, и `git check-ignore -v structure/graph.json`
  показывает это правило;
- [ ] `git status --short` не содержит строк структуры;
- [ ] резервные копии лежат в `<store>/backups/` и попадают в резервное
  копирование машины (store — вне репозитория, git его не сохранит).
