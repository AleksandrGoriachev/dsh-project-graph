# Чек совместимости плагина с версией DSH

Автоматическая часть — `tools/check-dsh-compat.mjs`, ручная — ниже. Прогоняется после установки
очередной версии DSH (сейчас ожидается **0.2.2-rc.1**, раскатана на 30 % установок).

## 1. Одна команда до установки (по npm-пакетам)

```powershell
node tools/check-dsh-compat.mjs --npm 0.2.2-rc.1 --skip-tests
```

Проверяет по опубликованным пакетам `@deepseek-ai/*` этой версии, что плагин найдёт нужные ему API:
`ctx.tools.register` и `ToolDefinition` (с обязательным `output`), `llm.listProviders/listModels`,
`subagent.getProvider`, `pluginManager.installBundle`, префиксные маршруты `webServer.prefixes`,
слот `conversation.view`. Ничего не устанавливает, ~30–60 с.

## 2. После установки (по установленному DSH)

```powershell
node tools/check-dsh-compat.mjs
```

То же по `app.asar` установленной версии плюс:

- версия DSH (из `dsh/package.json` внутри asar и из `FileVersion` exe);
- `node tools/test.mjs` — наборы API/CLIENT/GRAPH/RUNS/PANEL и т.д.;
- наши защищённые проверки: 0050 c1..c4, 0052 c1..c3, 0059 c1..c4, 0061 c1..c3, 0065 c1..c3,
  0067 c1..c4.

Итог: `совместимость подтверждена` (exit 0) или список `FAIL` с причиной. Полный прогон ~4 минуты.

Порт панели для проверки маршрута плагина можно передать явно:

```powershell
node tools/check-dsh-compat.mjs --port 51397
```

Ожидаемо: `HTTP 401/403` — маршрут зарегистрирован и требует авторизации; `HTTP 404` — плагин не
загрузился.

## 3. Ручная часть (5 минут)

| Шаг | Что сделать | Ожидаемо |
| --- | --- | --- |
| 1 | Открыть панель → вкладка **Structure** | схема рисуется, узлы на местах, ошибок загрузки нет |
| 2 | Клик по узлу `judge` | карточка: селекторы «Провайдер» и «Модель» заполнены из живого каталога |
| 3 | Сменить модель на `qwen3.8-flash` и сохранить | сохранение проходит; в `structure/graph.json` прямой `provider`+`model` |
| 4 | «Запустить узел» (или `project_graph_run`) по `judge` | ответ `status: ok\|error` с `output`, в журнале запусков запись |
| 5 | Во время шага 4 смотреть на узел | узел подсвечен «выполняется» (журнал запусков) |
| 6 | Панель обмена | папка и участники видны; неразрешённый участник даёт предупреждение, а не «0 писем» |
| 7 | `node tools/migrate-models.mjs --dry-run` | «изменений нет» (структура уже на прямых ссылках) |

## 4. Если что-то упало

Пришлите вывод команды из п. 2 целиком — в нём видно, какой именно API не найден и в какой версии.
Типичные сценарии:

- `FAIL tools: ctx.tools.register` — изменился контракт инструментов: правим `lib/spawn.js`,
  `lib/branch.js` под новую сигнатуру;
- `FAIL client: слот conversation.view` — переименован слот панели: правим регистрацию в `lib/client.js`;
- `FAIL маршрут плагина HTTP 404` — плагин не активировался: смотреть профиль `desktop` и лог
  `%USERPROFILE%\.dsh\logs\startup-*.log`;
- падают наши проверки — это регресс кода, а не версии DSH: разбираем как задание.

## 5. Что уже проверено сравнением версий (2026-11-04)

`0.2.1-rc.5` → `0.2.2-rc.1`:

- `dsh-llm`: 181 → 187 экспортов, **удалено 0**;
- `dsh-subagent`: 270 → 272, **удалено 0**;
- `dsh-session`: 70 → 70, идентично;
- `dsh-web`: 12 → 12, идентично;
- `dsh-tools`: внутренний рефакторинг (удалено 41, добавлено 33 — `Ptc*`, `ToolRuntimeScheduler`,
  `createRunCodeTool`), но `register(definition, options?)` и `ToolDefinition` совместимы; плагин
  ничего из `@deepseek-ai/*` не импортирует;
- `dsh-plugin-manager`: `installBundle`/`listBundles` на месте, манифест плагина
  (`dsh.bundle.patch`, `dsh.client.platform`) — `types/patch.js` и `types/registry.js` без изменений;
- клиентский контракт слотов `slots.d.ts` — 0 отличий, слот `conversation.view` есть.
