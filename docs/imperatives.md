# Императивы панели структуры

Дата: 2026-10-27. Источник: заказчик. Действуют на панель **Structure** и на
инструмент `project_graph_spawn`. Это не пожелания, а требования приёмки:
нарушение любого пункта — дефект, даже если данные прочитаны верно.

Образец подачи — панель **Workflow** (`subagent-workflow-v2`): подсказка на
каждом бейдже (`title` + `aria-label`), колонка «что означает» в таблицах
политики, пустые состояния объясняют, чего нет и что делать («В текущем
workspace нет workflow.config.json», «Реестр моделей пуст: семейство модели
проверить нельзя»), а не молчат.

## И-1. Ошибка = причина + что делать

Каждое сообщение об ошибке обязано содержать три части:

1. **что случилось** — человеческими словами, без жаргона;
2. **почему** — файл, узел, связь, модель или окружение, из-за которых это
   случилось;
3. **что сделать** — конкретное действие: правка файла, путь, команда, кнопка.

Запрещено:

- показывать пользователю голый код (`structure-invalid`, `unknown-node`) как
  единственный текст; код остаётся для машин и тестов, но идёт вторым;
- писать «ошибка валидации» без указания, что именно не так и где;
- смешивать ошибку данных (исправь `structure/*.json`) с ошибкой окружения
  (нет `roots`, нет папки, нет провайдера): у них разные рецепты;
- возвращать модели текст без подсказки: инструмент тоже обязан сказать, что
  проверить или исправить, а не только назвать код.

**Критерий приёмки.** Ни одного сообщения без глагола действия. Для каждого кода
валидатора и каждого отказа инструмента есть рецепт; рецепт проверяется тестом
(текст содержит действие и адрес).

## И-2. Каждый элемент графа объяснён

Объяснение получает **каждый** элемент, а не только узел:

| Элемент | Что обязано быть видно |
| --- | --- |
| узел | id, роль, модель, назначение (`brief`), что от него ожидать, пример задания или вклада, файл объявления |
| связь | вид (`delegate` / `review` / `peer`), направление, что это значит на практике, пример |
| роль | что это за роль в этом проекте, чем отличается от соседних |
| модель | алиас, `provider/model`, семейство, почему выбрана (если объявлено) |
| ошибка/предупреждение | по И-1 |

Форма подачи — как в Workflow: подсказка при наведении и фокусе
(`title` + `aria-label`), карточка деталей, колонка «что означает» в
таблицах. Пояснение обязано быть доступно **без чтения кода и без агента**.

Пустые значения не показываются прочерком: вместо «—» — объяснение, почему
значения нет и что это меняет («роль не задана: узел читается как исполнитель
без специализации»).

**Критерий приёмки.** У каждого типа элемента есть пояснение в UI; клиентский
тест проверяет наличие подсказки/пояснения, а не только подпись.

## И-3. Развитие схемы от узла — видимые опции

Выбор узла открывает меню **«Что дальше»**; все легальные следующие шаги
достижимы за ≤2 клика и подписаны:

- добавить связь `delegate` / `review` / `peer` **от этого узла**;
- назначить или сменить модель (список алиасов, не свободный текст);
- задать роль и назначение (`brief`);
- запустить агента по узлу (когда порождение включено);
- посмотреть кандидатов на связь и чем они отличаются.

Правила:

- у каждой опции есть подпись и подсказка с результатом действия;
- недоступная опция **не исчезает молча**: она видна, но объясняет причину
  («только чтение в v1», «у узла нет модели», «глубина исчерпана»);
- там, где есть список (модели, узлы, роли), — выбор из списка, а не ввод
  строки;
- меню не прячет разрушительные действия за иконкой без названия.

Меню узла выглядит так (уровни — раскрывающиеся подменю, не свободный ввод):

```
узел critic ▾
├─ Связь: delegate   → [список узлов: кому поручить]
├─ Связь: review     → [список узлов: кого проверять]
├─ Связь: peer       → [список узлов: с кем сотрудничать]
├─ Модель            → [алиасы: work / critic / …]
├─ Роль и назначение… (форма с подсказкой)
├─ Запустить агента   (недоступно: сначала назначьте модель)
└─ Кандидаты на связь (чем отличаются семейства моделей)
```

**Критерий приёмки.** С любого узла видны все допустимые продолжения схемы; ни
одна опция не показывается без подписи и подсказки.

## И-4. Открытие в воркспейсе

1. **Существующий воркспейс.** Панель определяет текущий workspace (рабочий
   каталог сессии / реестр воркспейсов) и по умолчанию показывает **его**
   топологию. Список проектов — переключатель, а не замена текущего.
2. **Нет `structure/`.** Вместо технического текста — человеческая инструкция
   «что это, зачем и как начать»: кнопки **«Создать иерархическую»**, **«Создать одноранговую»**, **«Создать смешанную»** и **«Создать без оценщика»**, которые по
   нажатию создают `structure/graph.json` с соответствующим стартовым графом
   (существующие файлы не перезаписываются), плюс ручной путь: 3–5 шагов, пример с
   пояснениями каждой строки и кнопка «Скопировать пример».
3. **Структура недействительна.** Показывать ошибки с рецептами по И-1, а не
   «структура недействительна».
4. **Язык — для человека.** В пустом состоянии и подсказках нет агентских
   формулировок («вызови инструмент», «JSON Schema», «провайдер не
   зарегистрирован» без перевода). Пишем так, как объяснили бы коллеге,
   впервые открывшему панель.
5. **Воркспейс вне `roots`** не игнорируется: панель либо показывает его,
   либо объясняет, как добавить, — без молчаливого переключения на чужой проект.

**Критерий приёмки.** Открытие в проекте без `structure/` даёт понятную
инструкцию и пример; открытие в проекте со `structure/` показывает его
топологию без ручной настройки `roots`.

## И-5. Автоматический обмен между воркспейсами узла «папка обмена»

Правило структуры (заказчик 2026-11-01): обмен идёт между воркспейсами, объявленными
в узле «папка обмена» (поле participants в structure/*.json), а не между подписями в
профиле. Обязанности инструмента:

1. список участников читается из узла; письма вне объявленных воркспейсов в обмен не
   попадают;
2. письмо доставляется автоматически, без участия человека, в пределах одного такта
   планировщика (30 с);
3. доставка не повторяется: память доставленного живёт на диске и переживает перезапуск;
4. одно пробуждение на пачку писем одного адресата; повторный старт — не раньше cooldown;
5. пробуждает только то, что требует действия: request, question, report, proposal,
   agreed, rejected; ack закрывает слот и молчит, answer — ответ, а не задача, и не
   будит (иначе ответ рождает ответ);
6. запись запуска честно разделяет намерение и факт: addressee — куда адресовано,
   cwd — где реально работал читатель, cwdSource — откуда известно, cwdMismatch —
   вычисленное расхождение;
7. двойников не бывает: агент не поднимается на письмо. Письмо лежит в ящике и
   читается собственным агентом стороны (живая сессия workflow пишет свои письма сама,
   без шапки Session). Спавн возможен только явным wakeSpawn: true для эксперимента;
8. доставка идёт в САМУ сессию адресата через штатный sessionController.prompt(request, signal)
   (второй аргумент — AbortSignal, не source). Холодная сессия резолвится хостом сама;
9. сессия, созданная маршрутом субагентов, прямой prompt не принимает («is owned by subagent
   routing»): такие пропускаются, берётся следующая по свежести (до трёх). Это ограничение
   хоста и признак двойников — их быть не должно.

Реализация: lib/exchange-watch.js, проверки — test/exchange-watch.test.mjs.

## И-6. Изменения — только через задание

Принцип заказчика: изменение кода и документов попадает в историю только через задание,
самовольных коммитов нет. В рабочей копии это обеспечивает гейт заданий (проверка перед
коммитом, метка осознанного обхода в сообщении, аудит диапазона коммитов) и разделение ролей:
контракт и проверки пишет архитектор, код — исполнитель отдельной сессией, приёмку — оценщик.

В публичной копии служебная часть гейта не публикуется: она завязана на внутренний движок
заданий. Сам принцип — часть подхода: сначала проверка, потом работа, потом приёмка.
