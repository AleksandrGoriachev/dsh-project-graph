# Бэклог

## 1. Узел графа показывает своё состояние (активность субагента)

Дата: 2026-10-28. Источник: заказчик. Приоритет: высокий.

**Требование.** Элемент графа обязан отображать состояние, а не только роль и
модель: если в текущий момент по узлу работает субагент, у узла должен быть
видимый признак активности.

**Состояния (минимум).**

| Состояние | Что означает |
| --- | --- |
| свободен | по узлу никто не работает |
| работает | субагент узла выполняется прямо сейчас |
| ждёт | субагент ждёт ответа или освободившегося слота |
| завершил | последний запуск закончился успешно, результат получен |
| ошибка | последний запуск завершился ошибкой |

**Откуда брать факт.** Каталог субагентов и их активность (проекция
`subagent/catalog` + статус сессии), а не догадки панели. Связь «сессия ↔
узел» — по `label` вида `role:node`, который ставит `project_graph_spawn`;
если метки нет, узел не подсвечивается.

**Статус 2026-10-28 (закрыто, кроме «ждёт»).** Реализованы «работает»,
«завершил», «ошибка», «свободен» и «нет данных»: `project_graph_run` и
`project_graph_spawn` пишут `running → done|error` в `runtime.runs`,
`GET /api/activity` отдаёт время и сообщение, детали показывают состояние.
Рамка активности — 3px, точка; источник running — сессии/каталог.

Слово состояния стоит **на самой карточке** (`lib/client.js`, `renderNode`,
`nodeState`): зелёное «работает», синее «завершил», красное «ошибка», серое
«свободен»/«нет данных»; то же слово в `aria-label` и в подсказке. Пока
активность не пришла, узел говорит «нет данных», а не «свободен» — панель не
врёт. Проверяется клиентскими тестами и `tools/preview.mjs` (слова на карточках
+ снимок).

**Решение заказчика 2026-10-28: состояние «ждёт» не показываем.** Вместо него
остаётся честное «нет данных», когда панель не знает состояние узла. Сигнала
«ожидает» в DSH нет, выдумывать его запрещено (И-1, приёмка 5). Пункт закрыт.

**«Ждёт» не реализовано и вот почему.** В DSH нет сигнала «ожидает»: строка
каталога субагентов содержит только `id`, `createdAt`, `mode` и `label`
(`dsh-subagent/lib/index.js`, `oneShotCatalogSchema`/`continuableCatalogSchema`),
а живой признак сессии — булев `running`. Придумывать состояние нельзя: это
нарушило бы И-1 (выдуманная причина) и приёмку 5. Нужно решение заказчика —
либо сигнал со стороны DSH, либо правило вида «запуск записан как running, а
сессия ребёнка не `running` → «ждёт подтверждения»».

**Как показывать.**

- на карточке узла: точка/бейдж состояния **и слово** (цвет не единственный
  признак), заметно на тёмной и светлой теме;
- в карточке деталей: состояние, кто именно работает, с какого времени;
- обновление по событию (проекция/SSE) или редким опросом; никакого опроса
  каждые 100 мс и фонового шторма;
- панель остаётся read-only: состояние только читается.

**API-набросок.** `GET /project-graph/api/activity?root=<abs>` → список
`{ node, state, sessionId?, label?, since? }`. Хост читает каталог субагентов;
клиент только рисует.

**Критерии приёмки.**

1. Запуск `project_graph_spawn` по узлу переводит узел в «работает» не позже
   чем через 2 секунды на живом DSH.
2. Завершение субагента снимает активность и показывает «завершил» или
   «ошибка» с причиной.
3. Состояние читается без наведения мыши: слово на карточке; `aria-label`
   содержит состояние.
4. Панель не пишет в проект и не создаёт своих таймеров чаще одного раза в
   секунду.
5. Если активность неизвестна, узел не врёт: показывается «нет данных», а не
   «свободен».

**Открытые вопросы.** Сколько состояний показывать в v1; хранить ли историю
запусков; что делать, если на узле несколько субагентов одновременно.

## 2. Адресат «последняя активная сессия» не видит спавны чужого воркспейса

Дата: 2026-11-01. Источник: workflow (--27 п. 5, --29 п. 5). Приоритет: средний.

**Факт.** Сессии, которые сторож поднимает для адресата (`cwd` = корень адресата),
хост пишет в каталог того проекта, из которого сделан спавн: три спавна 18:14–18:24
для `default-workspace` лежат в `~/.dsh/sessions/--C-Users-…-dsh-project-graph--/`, а
`readSessionActivity(default-workspace)` смотрит в `--C-Users-…-default-workspace--`.
Поэтому «последняя активная сессия воркспейса» по журналу такие сессии не видит;
остаётся сопоставление по `cwd` из списка живых агентов хоста, а после перезапуска
этот список пуст.

**Следствие.** Письмо для спящего воркспейса после перезапуска всегда идёт спавном
(`wake.reason: spawn`), даже если сессия адресата ещё жива в другом проекте хоста.
Тройной спавн по одному письму 01.11 вызван другим дефектом — памятью `seen` только в
процессе; она исправлена (файл `exchange-seen.json` рядом с записями запусков). Этот
пункт шире: правило «последняя активная» для кросс-проектных адресатов по журналу не
работает.

**Чего не хватает.** Источник «сессия → workspace/cwd» со стороны хоста (карта или
поиск агента по id). В имени каталога сессии закодирован проект хоста, а не `cwd`
сессии, поэтому по журналу адресата не восстановить.

**Решение на сейчас.** Дефект не маскируется: спавн — честный ответ «живой адресуемой
сессии нет». Риск «второй агент на то же письмо» снят диском; спавн на НОВОЕ письмо
при живом, но неадресуемом агенте остаётся и признаётся допустимым: ждать нечем.
## 3. Панель: объяснить «Внешнюю связь», «Перечитать факты», «Список фактов»

Дата: 2026-11-06. Источник: заказчик. Приоритет: средний (диагностика обмена).

**Что это сейчас.** Карточка «Внешняя связь» под схемой summarizes обмен: наше имя в обмене (`label`), строки
по контрагентам, счётчики писем ↗/↙ и «последнее <время>». Данные — `GET /api/exchange`: объявления
структуры (папки, контракты, участники), профиль (`exchange.me` / `participants`) и факты переписки.
«Перечитать факты» перезапрашивает `/api/exchange` и пересчитывает связи без перезагрузки панели.
«Список фактов» — полный список тех же связей, открывается кнопкой из редактора/портала.

**Почему предупреждение «имя этого воркспейса в обмене не объявлено».** Панель не нашла метку, чей путь
совпадает с корнем: ни `exchange.me`, ни запись в `participants`. Тогда квитанции подписываются именем
каталога — оно может случайно совпасть с меткой контракта (обмен валиден), но держится на имени папки:
переименование ломает подпись. Лечится строкой профиля `participants: { <метка>: <абсолютный путь> }`
или `exchange.me: <метка>` (и «Перечитать факты» после правки).

**Что сделать.** Подсказки (title/aria) у метки, счётчиков и обеих кнопок; раскрываемая справка карточки
«что это и откуда данные»; в состоянии «имя не объявлено» — готовый пример строки профиля и кнопка
«Проверить после правки» (= перечитать); «Список фактов» — колонки «кто / направление / сколько / последнее»
и та же справка.

## 7. Планировщик: служебная сессия без агента (headless-create-failed)

Дата: 2026-11-07. Источник: заказчик (разбор ошибки). Приоритет: высокий. Статус: **в очереди после 0133**.

**Что случилось.** Ночной запуск узла по расписанию не состоялся: в воркспейсе не было живой сессии,
планировщик попросил хост поднять служебную сессию, хост вернул её без привязки к агенту
(`agent id "undefined" does not match session id "session-1"`), проверка тождества отклонила запуск.
Отчёт за окно не сформирован, прогон не выдуман — это правильно; в журнале остался технический код.

**Требование.**

1. Создавать служебную сессию так, как ждёт текущий хост: агент и сессия обязаны совпадать по id;
   если хост вернул сессию без агента — пробовать согласованный путь (явная привязка), а не молча падать.
2. Если сессию поднять нельзя — писать понятную причину «нет живой сессии» с окном и следующим запуском,
   технический код хоста — только в раскрываемых деталях.
3. Панель показывает человеческую формулировку: что должно было произойти, что помешало, что теперь,
   что делать человеку. Технические коды не в первой строке.
4. Журнал расписания: причина `сессия без агента` + окно + следующий запуск, без потери исходной строки хоста.

**Приёмка.** Тест «хост вернул сессию без агента» → понятная причина и отсутствие ложного прогона;
тест «хост поднял сессию с агентом» → прогон стартует; панель на фикстуре показывает человеческий текст;
журнал содержит окно и следующий запуск. Регресс: 0084 (headless), 0110 (две попытки), 2.6.42 (launch-evidence).

## 8. Панель может перезаписать structure/graph.json устаревшей моделью (потеря рёбер)

Дата: 2026-11-07. Источник: инцидент. Приоритет: высокий. Статус: **в очереди после 0136**.

**Что случилось.** Ребро `worker → judge (review)` было добавлено коммитом f904408, но после правок панели
(позиции узлов, a45ec6c/16eaab8) ребро исчезло из файла: панель сохраняет граф целиком из своей модели,
и если модель была прочитана до правки файла (или собрана из другого источника), сохранение затирает чужие
изменения. Спавн 0133 упал на `task-contradicts-structure`, потому что приёмщиком стал reviewer-1.

**Требование.**

1. Сохранение графа из панели обязано не терять рёбра/поля, которых не было в её модели: перед записью
   перечитывать файл и применять только те изменения, что сделал пользователь (или отказывать с причиной).
2. Проверка: правка ребра в файле при открытой панели → сохранение позиции узла не удаляет ребро.
3. Журнал: сохранение, затронувшее чужие изменения, пишет факт в health/аудит.

**Приёмка.** Тест «файл изменён извне между чтением и сохранением» → ребро на месте либо отказ с причиной;
регресс: 0021/0022 (сохранение узла/папки), 0117 (гейт записи).
