# План реализации 0002 (черновик, после выбора варианта)

Дата: 2026-10-28. Статус: **черновик**, задачей workflow станет после того, как
заказчик выберет вариант из 0001. Пока это не контракт: гейты его не читают.

## Почему отдельной задачей

0001 — только анализ и три варианта, код в нём не меняется. Реализация зависит от
выбора заказчика, поэтому её нельзя оформить заранее: критерии приёмки будут
отличаться у каждого варианта.

## Что войдёт в 0002 (по любому варианту)

1. Изменения в `lib/client.js` (и, если нужно, `lib/graph.js` — только чтение
   данных, без изменения валидатора).
2. Тесты: клиентские (`test/client.test.mjs`) и браузерный прогон
   `tools/preview.mjs` — новые подсказки и состояния обязаны быть проверены, а не
   только нарисованы.
3. Обновление `README.md` (как выглядит подача) и `HANDOVER-NEXT.md`.
4. Критерии: три наблюдаемых поведения (подсказка доступна с клавиатуры; состояние
   видно без наведения; ошибка объясняет «что сделать») плюс «вне разрешённых путей
   правок нет».

## Порядок, когда заказчик скажет «делаем»

1. Развернуть воркфлоу в репозитории панели:
   `node <спека>/scripts/init.mjs --repo C:/Users/Goryachev/Documents/deepseek-harness/dsh-project-graph`.
2. Закоммитить контракт 0001 (task.md, criteria.json, checks/design-0001.mjs) и
   зафиксировать его `task-hash --write`.
3. `task-red` — критерии C1–C4 обязаны упасть на базе, C5 пройти.
4. Запустить `designer` через структуру: `project_graph_run` (или ветку
   `coordinator → designer`, если нужен план координатора).
5. Приёмка `judge` отдельной сессией + `task-check-acceptance`.
6. Следить за состоянием узлов в панели и за стадией задачи в консоли Workflow.

## Мониторинг (что смотрю я)

- `GET /project-graph/api/activity?root=…` — состояние узлов, шаги ветки по
  `branchId`, ошибки с сообщением;
- `GET /workflow/api/tasks` — стадия задачи, флаги, `releaseReady`;
- при расхождении (например, узел «завершил», а задача не сдвинулась) — стоп и
  разбор причины, а не повторный запуск.
