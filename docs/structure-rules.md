# Правила структуры

Дата: 2026-11-01. Основание: расклад ролей заказчика и переписка threads/critic-report.
Это над-воркспейсная настройка: файл читают агенты structure и исполнители, назначенные структурой.
Машинного поля `rules` в `structure/graph.json` нет, поэтому правило живёт здесь и версионируется
git. Изменение — правкой файла с датой, основанием и подписью. Требование стороны workflow —
`C:\\Users\\Goryachev\\Documents\\deepseek-harness\\coordination\\CONTRACT-exchange-delivery.md`;
при расхождении приоритет у контракта (он — требование к инструменту), а этот файл описывает, как
structure его исполняет.

## П-1. Роли (заказчик, 2026-11-01)

1. **structure** — над-воркспейсная настройка: узлы, роли, связи, правила. Она не встраивается в
   приложения и плагины и не владеет их кодом; сама `lib/` и `test/` не правит.
2. **Исполнитель** — узел `worker` (роль «исполнитель», модель `work` = deepseek-official/deepseek-flash).
   Он правит `lib/` и `test/` по заданию structure.
3. **Приёмщик** — узел `judge` (роль «приёмщик»). В `structure/graph.json` связь
   `worker --review--> judge`, поэтому ожидаемый приёмщик работы worker — judge
   (`lib/contract.js`, `expectedAcceptor`).
4. **workflow** — формулирует требование и принимает результат по следам (файл, сообщение, запись
   запуска); в код не лезет, дефект — письмо `Status: request`.
5. Назначение исполнителя фиксируется правилом и заданием; запуск — `project_graph_run` по узлу
   `worker`. Второй писатель в один файл не запускается: пока в файле работает живая сессия,
   следующий запуск ждёт.

## П-2. Доставка письма в воркспейс адресата (принято 2026-11-01, письмо workflow --45)

Требование: `coordination/CONTRACT-exchange-delivery.md`. Фаза B (сейчас); исполнитель — узел
`worker`, приёмщик — `judge`, независимая приёмка — workflow. E1 — фаза A, после появления API
хоста; в текущий объём не входит.

1. Запись запуска `kind: exchange` содержит: `addressee` (куда адресовано), `cwd` (что
   попросили у хоста), `agentCwd` (где агент работал на самом деле), `cwdSource` (`session` — из
   дескриптора живой сессии, `journal` — из журнала сессии, `requested` — факта нет), `cwdMismatch`,
   `wake { target, reason }`, `delivered`, `state`.
2. `state` — `running | done | error | partial` (изменено 2026-11-01 20:16; основание — письмо
   workflow --52 от 20:15 и разбор E2). `partial` = «доставлено, но место работы не доказано»:
   приёмка не вправе прочитать намерение как факт. Прежняя редакция («`partial` не вводится,
   расхождение видно полем») снята: при неизвестном факте единственная альтернатива — либо
   `cwdMismatch: true` (утверждение о расхождении, которого никто не наблюдал), либо молчание поля;
   обе формы выглядят как отчёт о факте, которым не являются. `done` без факта о месте работы
   не ставится.
3. Место работы — два разных поля (изменено 2026-11-01 20:16, основание — workflow --52):
   `cwd` — что попросили у хоста, `agentCwd` — где агент работал на самом деле, `cwdSource` —
   откуда факт (`session` — дескриптор живой сессии, `journal` — журнал сессии, `requested` —
   факта нет), `cwdMismatch` считается от `agentCwd` и равен `null`, когда факта нет.
   `done` — только при известном `agentCwd` внутри `addressee` (`cwdMismatch: false`);
   `partial` — факт неизвестен; `true` — факт есть и он вне адресата.
   `record.identity.cwd` в кэше сессии фактом НЕ является: это cwd родителя, записанный при
   создании (`lib/live.js:184–229`); факт — `record.rows.workingDirectory.val` и первая запись
   `working-directory/change` журнала.
   Отсюда E2 читается так: спавн → `done` + `agentCwd` внутри адресата + `cwdMismatch: false` +
   `wake.reason: spawn`. Прежнее ожидание «done + cwdMismatch: true» было суррогатом на случай
   отсутствия факта и этой редакцией снято; что доставка сделана спавном, а не в живую сессию,
   говорит `wake.reason`.
4. Критерии E2, E3, E4, E5, E6 — приняты. E1 (живая сессия → done в cwd адресата) — фаза A.
5. Не откатывать: `dfb6b25` (cwd в записи, с тестом) → `63c7cea` (дубль ключа) → `dd0b4ad`
   (addressee, cwdSource, cwdMismatch; дубль убран). `acd0535` (участники из узла) — тоже.
   `0a9c1f2` в репозитории не существует (опечатка в письме structure --24; `git cat-file -t`
   отвечает `fatal: Not a valid object name`).

## П-3. Обмен между воркспейсами

1. Участники — только из узла `exchange` (`participants`) в `structure/graph.json`; профиль даёт
   метки, не участников (`declaredExchangeWorkspaces`, коммит acd0535).
2. Папка обмена — `coordination`; спеки — `docs/exchange.md` в каждом воркспейсе
   (блок `dsh-exchange:begin/end`).
3. `ack` не будит адресата и закрывает слот. `answer` не будит (dd0b4ad): ответ читает эта же
   сторона на следующем шаге. Полный перечень будящих статусов — в коде
   (`lib/exchange-watch.js`, `WAKE_STATUSES`).
4. `proposal | agreed | rejected` пока остаются будящими (structure --30, 19:53). Снятие `answer`
   безопасно: письмо-ответ отвечает тому, кто спрашивал и уже работает. `proposal` — задача, и в
   спящем воркспейсе её никто не прочтёт, поэтому эти три снимаются только по замеру петель, а не
   по аналогии. Порядок: сначала замер, потом правка.

## П-4. Прогоны обмена

Тесты и проверки обмена — только с подменённым `USERPROFILE` на временный каталог: телеметрия
пишется в жёсткий путь `~/.dsh/project-graph/exchange-watch.json`, без подмены прогон засоряет
живой файл и при >200 КБ может выбросить живые строки, на которые ссылается приёмка
(найдено 2026-11-01, письмо workflow --44 §4).
