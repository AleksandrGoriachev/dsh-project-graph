# Спека: эргономика подсказок и сообщений о состоянии графа

Дата: 2026-10-28. Заказчик: сторона `structure` (панель Structure).
Исполнитель: узел `designer` структуры проекта.
Результат: **документ с тремя вариантами решения** и рекомендацией. Код не меняется —
реализация будет отдельной задачей после выбора заказчика.

## 1. Зачем

Панель Structure показывает граф проекта, состояние каждого узла, подсказки и
сообщения об ошибках. Сейчас всё это есть, но подача накапливалась по частям:
подсказка живёт в `title` у SVG-группы, состояние — мелким словом на карточке и
строкой в карточке деталей, ошибки — списком под графом. Человек, открывший
проект впервые, не понимает, где смотреть, а опытный — тратит клики.

Нужно три варианта, как сделать подачу подсказок и сообщений о состоянии
эргономичнее, не ломая существующие механизмы и оставаясь в возможностях
клиента.

Ограничения DSH, которые нельзя обойти выдумкой:

- состояния «ждёт» нет: каталог субагентов отдаёт `id/createdAt/mode/label`, сессия —
  булев `running`. Нельзя рисовать «ждёт», если сигнала нет;
- клиент — классический браузерный модуль: `window.__ModuleLoader__.load`,
  `React.createElement`, без JSX и сборки, без внешних зависимостей;
- граф — SVG; карточки и формы — HTML в React;
- панель только читает структуру и пишет в неё через свои маршруты; состояние
  берётся из `/project-graph/api/activity` (опрос раз в 2 с) и
  `/workflow/api/status` (по нажатию).

## 3. Три области, которые обязан закрыть каждый вариант

1. **Эргономика.** Где человек ищет, что делает без лишних кликов; что должно быть
   видно сразу, что по фокусу, что в деталях. Порядок действий для трёх сценариев:
   «впервые открыл проект», «нашёл проблему и исправляю», «смотрю, что делает агент».
2. **Подсказки.** Как показать смысл элемента (роль, модель, связь, состояние) так,
   чтобы не приходилось угадывать: `title`, встроенный текст, панель, раскрытие,
   легенда. Обязательно: доступность с клавиатуры, `aria`, цвет — не единственный
   признак, пустое значение объясняется, а не показывается прочерком.
3. **Сообщения о состоянии.** Как сообщать, что узел делает, что ветка идёт, что
   запуск упал и почему, что установка workflow требует перезапуска. Сообщение
   обязано отвечать на три вопроса (И-1): что случилось, почему, что сделать.

## 4. Что обязано быть в документе

Один файл `docs/design/ui-ergonomics/0001-variants.md` со структурой:

```markdown
# Варианты подачи подсказок и состояний

## Вариант 1. <название>
### Идея
### Что видит человек
### Подсказки
### Состояния
### Компромиссы
### Цена
### Риски

## Вариант 2. <название>
(те же подзаголовки)

## Вариант 3. <название>
(те же подзаголовки)

## Сравнение
| | Вариант 1 | Вариант 2 | Вариант 3 |
| --- | --- | --- | --- |
| Что меняется | | | |
| Цена | | | |
| Риски | | | |
| Ложится на текущий код | | | |

## Рекомендация
Один вариант и почему. Если рекомендуете не один, а комбинацию — скажите, что
берёте из каждого и почему это не «среднее из трёх».

## Открытые вопросы
Что должен решить заказчик до реализации.
```

Требования к содержанию:

- **конкретика вместо общих слов**: где именно на экране, какой элемент, что
  происходит при наведении, фокусе, клике; какие файлы и функции придётся менять
  (можно назвать функции из `lib/client.js`);
- **цена**: S (≤1 день), M (2–3 дня), L (неделя и больше) — по вашему опыту, с
  разбивкой на шаги;
- **риски**: что сломается в тестах, предпросмотре, доступности, на узком экране;
- **каждый вариант покрывает все три области** из раздела 3 — не «только
  подсказки»;
- **нельзя предлагать состояния, которых нет в данных**; если для варианта нужен
  новый сигнал — прямо напишите, какой и от кого.
